          reads the server every 10 s while it runs and keeps 24 hours of
          readings in its database. They come back averaged into steps
          (`step_seconds`: 10, 60 or 240), 360 points at most per series, oldest
          first, each at the start of its step. A step without a reading —
          ferryd was stopped — has no point, so a gap between two points is a
          time without data. The host: CPU use (0–100 % of the machine), memory
          used and total, the read / write speed of its disks together and the
          network traffic, like `GET /api/v1/server/metrics`. The containers:
          the 5 service instances and datastores whose CPU use (100 = one core)
          was the highest in the range, the busiest first, with their memory. A
          value that could not be read in a whole step is `null`. The requests,
          which the proxy counts and ferryd stores every 10 s: `requests` has
          the services' together (neither the dashboard's nor the unrouted ones)
          for every step ferryd ran in and stored requests for — the requests
          per second over `seconds` (the step, or less for the last one, still
          filling), the requests by status class, and the p50 and p95 latency in
          milliseconds, `null` in a step without a request to time — and
          `request_targets` each target that had requests over the whole range,
          the services busiest first, then `dashboard` and `unrouted`.
          Percentiles come from a histogram with fixed buckets: they are exact
          to the bucket."

      - content: "ferryd's own log: the lines it prints to its standard output (the
          terminal, `ferryd.log` or the service manager), as values. The server
          keeps its last 2,000 lines in memory, from its start, the same with
          `ferryd start` and `ferryd run`, and writes nothing more to disk:
          older lines are only in its output. It logs `info` lines and above,
          and `debug` lines when `RUST_LOG` asks for them: those of Ferry itself
          are kept here, those of the libraries it uses only in its output. A
          line longer than 8 KiB (its message and fields together) is cut. A
          follower that falls behind never slows the server down: it misses
          lines, and an `event: skipped` says how many."

          `ferry_host_disk_written_bytes_total` (by `mount_point`),
          `ferry_host_network_receive_bytes_total` and
          `ferry_host_network_transmit_bytes_total` (by `device`: each interface
          but the loopback and Docker's own) — the CPU seconds and the disks'
          bytes count from the start of the machine, an interface's bytes from
          its own start. The containers, every running service instance and
          datastore by `kind`, `id`, `name` and `instance_id` (services only;
          not `instance`, which Prometheus gives the target):
          `ferry_container_cpu_percent` (100 = one core) and
          `ferry_container_memory_bytes`. The requests, by `target` (a service
          id, `dashboard` or `unrouted`) and `name`:
          `ferry_http_requests_total{status_class}` (`2xx` to `5xx`) and the

          headers, WebSockets left out), counted from the start of ferryd. A
          value the server can't read (on macOS, most host values) is left out,
